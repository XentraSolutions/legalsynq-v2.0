# TB-DATA-01 — TenantId ↔ Commerce BillingAccount Mapping

## Goal

Add a first-class **TenantBillingProfile** aggregate to the canonical Tenant
Billing service (`services/tenant-billing/`, `Billing.*` assemblies) that maps
each tenant id to the Commerce-side **BillingAccountId** that represents that
tenant's billing relationship with the platform.

This is the data-layer foundation block. It deliberately does **not**:

- merge the two billing domains (tenant-billing tables and commerce billing
  tables remain physically and logically separate);
- add a project reference between Billing and Commerce (`BillingAccountId` is
  stored as a primitive `Guid`, treated as an opaque external reference);
- perform any live HTTP call to the Commerce service (resolution is purely a
  local read against the Billing database);
- introduce changes to Identity, Control-Center or Tenant-Portal flows.

## Surface

* `Entities/TenantBillingProfile.cs` — aggregate root with the lifecycle
  (Draft → Active → Suspended → Closed) plus a free-standing **BillingMode**
  (Disabled / InternalOnly / TenantOperated / PlatformManaged) so a downstream
  resolver can decide whether to *use* the mapping at all.
* `Entities/TenantBillingProfileStatus.cs` — string-constant set, mirroring
  `InvoiceTemplateStatus`.
* `Entities/TenantBillingMode.cs` — string-constant set.
* `Repositories/ITenantBillingProfileRepository.cs`.
* `Services/ITenantBillingProfileService.cs` (+ exceptions
  `TenantBillingProfileConflictException`,
  `TenantBillingProfileNotFoundException`,
  `InvalidTenantBillingProfileTransitionException`).
* `Services/TenantBillingProfileService.cs` — create / lookup / list /
  activate / suspend / close.
* `Services/ITenantBillingAccountResolver.cs` (+ implementation
  `TenantBillingAccountResolver`) — narrow read interface
  `Task<Guid?> GetBillingAccountIdAsync(Guid tenantId, ct)` that other
  Billing-side flows can inject without needing the full service surface.
  Returns the BillingAccountId of the **Active** profile for the tenant, or
  null if none.

### Infrastructure (`Billing.Infrastructure`)

* `Repositories/TenantBillingProfileRepository.cs` — EF-backed repo with the
  same patterns as `CustomerRepository` (no-tracking reads, AddAsync /
  UpdateAsync writes, paged list).
* `Data/BillingDbContext.cs` — `DbSet<TenantBillingProfile>` plus an
  `OnModelCreating` block that mirrors the InvoiceTemplate
  computed-column pattern: a stored generated column **`ActiveScopeKey`**
  that is non-null only for non-Closed rows, indexed UNIQUE on
  `(TenantId)` AND on `(BillingAccountId)`. Skipped on the InMemory provider
  (tests rely on the service-level guard for the same invariant).
* `Data/Migrations/20260515120000_TenantBillingProfiles.cs` (+ minimal
  Designer placeholder, matching the WRITE-005 / ERP-001 / ERP-003
  precedent — the project-level model snapshot is regenerated by the
  maintainer in a dotnet-SDK-equipped environment before the next
  schema-touching migration).
* `DependencyInjection.cs` — register repo + service + resolver.

### API (`Billing.Api`)

* `Contracts/TenantBillingProfileDtos.cs`:
  * `CreateTenantBillingProfileRequest`
  * `TenantBillingProfileResponse`
  * `TenantBillingProfileListResponse`
* `Controllers/TenantBillingProfilesController.cs` mounted at
  `api/tenant-billing/profiles`. All routes are tenant-scoped via the existing
  `TenantResolutionMiddleware` (`X-Tenant-Id`) and gated by the existing
  `RequireInternalTokenMiddleware` (`X-Internal-Token`) — the controller
  itself adds no new auth. Endpoints:
  * `POST   /api/tenant-billing/profiles` — create a Draft profile binding
    `(TenantId from header) → BillingAccountId in body` with optional
    `HostPlatformKey` + `ExternalTenantId` mirror fields.
  * `GET    /api/tenant-billing/profiles` — paged list of profiles for the
    request tenant.
  * `GET    /api/tenant-billing/profiles/{id:guid}` — single fetch.
  * `GET    /api/tenant-billing/profiles/by-billing-account/{billingAccountId:guid}`
    — exact match for the request tenant's profile pointing at a given
    BillingAccountId. Returns 404 when no match.
  * `POST   /api/tenant-billing/profiles/{id:guid}/activate`
  * `POST   /api/tenant-billing/profiles/{id:guid}/suspend`
  * `POST   /api/tenant-billing/profiles/{id:guid}/close`

  All handlers map domain exceptions to ProblemDetails:
  `TenantBillingProfileNotFoundException` → 404,
  `TenantBillingProfileConflictException` → 409,
  `InvalidTenantBillingProfileTransitionException` → 409,
  `ArgumentException` → 400.

## Lifecycle / invariants

* **Statuses**: Draft, Active, Suspended, Closed. Transitions:
  * Draft → Active (Activate)
  * Active → Suspended (Suspend)
  * Suspended → Active (Activate again)
  * Active → Closed (Close)
  * Suspended → Closed (Close)
  * Draft → Closed (Close — abandoned mapping)
  * Closed is **terminal**.
* **Uniqueness** (enforced both in service and at the relational layer):
  * At most one **non-Closed** profile per `TenantId`.
  * At most one **non-Closed** profile per `BillingAccountId`.
  * Multiple historical Closed rows are allowed (audit trail of past
    mappings — e.g. a tenant being re-mapped after a billing migration).
* **Tenant scoping**: every read is filtered by `TenantId` from the
  middleware-resolved tenant context. A caller that knows another tenant's
  profile id cannot read or mutate it (mismatched tenant returns 404).

## Resolver contract

`ITenantBillingAccountResolver.GetBillingAccountIdAsync(tenantId)` is the
narrow seam future Billing-side flows can depend on without taking the full
profile service. It returns the BillingAccountId of the tenant's **Active**
profile, or null if the tenant has no profile or only Draft / Suspended /
Closed profiles. Suspended/Draft are intentionally excluded so a resolver
caller (e.g. a future "post charge to Commerce" flow) automatically stops
honouring the mapping while a tenant is paused, without each caller having to
re-implement the rule.

## Out of scope

* Calling Commerce to verify the BillingAccountId exists. The mapping is
  asserted by an internal operator (the BFF / admin tooling) and Billing
  trusts the value as opaque.
* Two-way sync. Status changes on the Commerce-side BillingAccount do **not**
  flow back to update the profile here. A follow-up block can add a reconciler
  job that calls the Commerce read API and reflects status drift; that job
  would consume `ITenantBillingProfileService` rather than touching tables
  directly.
* Identity / Tenant-Portal UI. The admin surface for editing profiles will be
  added in a later block; this one ships only the REST + domain layer.
