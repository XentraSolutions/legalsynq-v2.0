ARCHITECTURAL PRINCIPLE
Synq Intake is tenant-bound, product-neutral, independently deployable, and source-preserving.

Synq Intake owns:
- tenant Intake configuration
- processing-profile definitions
- tenant/profile assignments
- validated profile configuration
- configuration versioning
- configuration resolution
- Intake-owned persistence

Synq Intake does NOT own:
- tenant master data
- organization master data
- users
- cases
- liens
- patients
- facilities
- providers
- document binaries
- Flow tasks/workflows
- notifications
- AI vendor credentials
- downstream product databases

Do not add direct implementation dependencies from Intake to:
- Liens.Infrastructure
- Fund.Infrastructure
- CareConnect.Infrastructure
or equivalent product-specific implementation assemblies.

Use contracts/APIs/adapters/events later where product interaction is needed.

OBJECTIVE
Build the persistent tenant-scoped configuration framework that controls how Synq Intake behaves for each tenant without coupling Intake to SynqLien, SynqFund, or CareConnect.

The completed framework must be able to answer:

“For this authenticated tenant, which Intake processing profile applies, is it enabled, what validated configuration governs it, and which configuration version was used?”

LIEN_INTAKE_V1

==================================================

- resolve Tenant B processing configuration
- set Tenant B default profile

- infer Tenant B configuration

Server-side tenant filtering is mandatory.

Do not rely on UI filtering.

Do not treat an arbitrary TenantId in a request body as authoritative.

Use the established LegalSynq JWT/service-token/tenant-context patterns.

Administrative explicit-tenant operations may only exist if the current platform already has a consistent authorized pattern.

==================================================
8. VERSIONING AND CONCURRENCY
==================================================

Implement optimistic concurrency.

At minimum:
- TenantIntakeConfiguration.ConfigurationVersion
- TenantProcessingProfile.ConfigurationVersion

Behavior:
- initial version = 1
- each successful mutation increments version
- stale client update must not silently overwrite a newer version
- stale update should return HTTP 409 Conflict

Example:
- client reads version 4
- another update creates version 5
- client attempts update based on version 4
- result must be conflict, not overwrite

Reuse existing LegalSynq concurrency conventions if available.
