LOCKED ARCHITECTURE
==================================================

1. Xenia is an independent, separately deployable automation platform.

2. Email is a module within Xenia.

3. LegalSynq is the first host platform, not the owner of Xenia core.

4. Xenia remains tenant-aware and provider-neutral.

5. Provider-specific code belongs only in provider connectors and provider mappers.

6. Xenia must not directly access another service’s database.

7. Credentials remain outside the Xenia database.

8. Secret values must be resolved only through the secret-reference abstraction.

9. Xenia owns:

- Email synchronization orchestration
- Provider cursor state
- Canonical message model
- Normalized message persistence
- Duplicate detection
- Ingestion-run tracking
- Attachment-reference metadata
- Retry and resume state
- Email message APIs
- Message administration UI APIs

10. Documents service owns:

- Attachment binary storage
- Document lifecycle
- Document versioning
- File retrieval

11. Audit service owns durable audit persistence.

12. Xenia must not persist attachment binaries.

13. Xenia must not persist mailbox credentials.

14. Xenia must not contain LegalSynq product-domain logic.

15. The Email ingestion engine must be reusable by another host platform without redesign.

15. IMPLEMENT DUPLICATE DETECTION
--------------------------------------------------

Create IDuplicateDetectionService.

Signals in order:

1. TenantId + EmailSourceId + ProviderMessageId
2. TenantId + EmailSourceId + InternetMessageId
3. Provider cursor evidence
4. Canonical content hash fallback

Rules:

- ProviderMessageId is the strongest source-scoped identity.
- InternetMessageId is a cross-provider signal but not universally reliable.
- Hash fallback must avoid false positives.
- Duplicate detection must be deterministic.
- Duplicate imports must not create duplicate attachment records.
- Existing messages may have metadata refreshed.
- Body content should not be overwritten blindly when existing content is more complete.
- Duplicate events must be recorded in ingestion-run counts.
- Duplicate audit events must not include body content.

Add tests for:

- Exact provider duplicate
- Same InternetMessageId from same source
- Same InternetMessageId from different sources
- Missing InternetMessageId
- Hash collision protection
- Updated provider metadata
- Attachment duplicate behavior
- Concurrent import race

Use database unique constraints as a final safety layer.
