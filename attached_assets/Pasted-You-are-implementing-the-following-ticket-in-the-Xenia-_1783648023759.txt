LOCKED ARCHITECTURE RULES
==================================================

1. Xenia is an independent service.

2. Xenia must be deployable separately from LegalSynq.

3. Xenia core must not directly depend on:
   - LegalSynq database schemas
   - LegalSynq case models
   - LegalSynq lien models
   - LegalSynq funding models
   - LegalSynq workflow internals
   - LegalSynq-specific user models
   - LegalSynq-specific business rules

4. Platform dependencies must be accessed through replaceable adapter interfaces.

5. Xenia must be tenant-aware.

6. Tenant context must be explicit and must not rely on unrestricted caller-supplied tenant identifiers.

7. Future modules must be registerable without changing core orchestration logic.

8. The module framework must support:
   - Module identity
   - Name
   - Version
   - Enabled or disabled state
   - Runtime status
   - Health status
   - Configuration namespace
   - Future lifecycle hooks

9. Xenia must own its internal operational data.

10. Shared platform services remain external capabilities.

11. Do not create direct cross-service database access.

12. Keep interfaces small, typed, documented, and replaceable.

13. Build only the minimum adapter implementations needed for local or development operation.

14. Placeholder adapters must fail safely and report an honest unavailable or unconfigured status.
